# LFD121 4장 — 공개 설계 (Open Design)

2026-11-17 · 적용한 곳: [api-security-supply-chain](https://github.com/zeldaim/api-security-supply-chain), [ml_detection](https://github.com/zeldaim/ml_detection) 등 내 레포 공개 전환

보안은 설계를 숨기는 데 기대면 안 된다. 설계가 다 알려져도 안전해야 하고, 숨겨야 하는 것은 비밀번호나 키 같은 작고 바꿀 수 있는 비밀뿐이다.

## 개념

- Saltzer & Schroeder 의 설계 원칙 중 하나. 암호학의 케르크호프스 원칙과 같은 이야기다. 알고리즘은 공개돼도 되고 키만 비밀이면 된다.
- 반대말이 "숨겨서 지키는 보안(security through obscurity)" 이다. 숨긴 것은 언젠가 드러나고(리버싱, 유출, 퇴사자), 드러나는 순간 방어가 통째로 무너진다. 키는 바꾸면 되지만 설계는 바꾸기 어렵다.
- 숨기는 것 자체가 금지는 아니다. 추가 층으로는 괜찮지만, 유일한 방어가 되면 안 된다.
- 공개하면 많은 사람이 검토해서 결함을 더 빨리 찾는다. 보안 도구 다수가 오픈소스인 이유다.

## 원래 상태

| 프로젝트 | 위치 | 문제 |
|---|---|---|
| 팀 쇼핑몰 (API 보안 프로젝트의 대상) | `GET /api/v1/users/{id}` | 명세에 없는 옛 경로라 문서에서는 안 보였지만, 인증 없이 남의 정보를 돌려줬다 (BOLA). "아무도 모른다"가 유일한 방어였다 |
| ml_detection (공개 전 원본) | 커밋 `eab0387` | 팀 쇼핑몰 `.env` 2개와 팀원 실명 폴더가 이력에 남아 있었다. 설계와 비밀이 한 레포에 섞여 있었다 |

## 적용

**1) 숨은 경로를 찾아 숨김이 아닌 인증·권한으로 막혀 있는지 본다**

내 API 보안 프로젝트가 하는 일이 이 원칙의 검사다. 명세에 없는 경로(Shadow API)를 소스, 설정, 로그, 스캔 4가지 출처로 찾고, 사람이 승인한 것만 기준으로 삼는다.

**2) 레포를 공개하면서 설계와 비밀을 나눴다**

| 공개 (설계) | 비공개 (비밀) |
|---|---|
| 탐지 룰 생성 방식, 파이프라인 코드, Terraform, 평가 방법 | `.env` 의 JWT 키 · DB 비밀번호, 실명, 원본 운영 로그 |
| 공개 레포 | 비공개 보관 레포 `team-raw-archive`, 또는 삭제 |

- 공개 전에 gitleaks 로 이력 전체를 검사했다.
- `ml_detection` 은 원본을 그대로 공개하지 않고, 이력을 새로 시작한 사본을 공개했다. 원본은 `ml_detection_work`(비공개)로 두었다.
- DR 프로젝트의 Terraform 은 공개돼 있지만 DB 비밀번호는 코드에 없고 변수와 SSM 으로 받는다.

**3) 탐지 룰을 공개해도 되나**

공격자가 룰을 보고 피해 갈 수 있다는 걱정이 있다. 이 원칙대로라면 룰이 공개돼도 탐지가 유지되게 만드는 것이 맞다. 120초 빈도 룰은 천천히 하면 피해져서 느린 BOLA 를 놓쳤는데, 숨겨서 해결할 문제가 아니라 룰을 바꿔야 했다. 다만 운영 중인 실제 임계값은 키처럼 바꿀 수 있는 설정값으로 보고 공개본에 넣지 않는다.

## 내 다른 글 · 프로젝트와 연결

- 같은 장에서 먼저 정리한 [최소 권한](ch04-least-privilege.md) 과 이어진다. 한 문장으로: 설계는 공개하고, 방어는 권한으로 한다. 최소 권한으로 관리 서버의 `AdministratorAccess` 를 쪼개 놓았기 때문에 그 정책 코드가 공개돼도 안전하다.
- 적용한 프로젝트: [api-security-supply-chain](https://github.com/zeldaim/api-security-supply-chain) (숨은 API 찾기), [multicloud-dr-petclinic](https://github.com/zeldaim/multicloud-dr-petclinic) (최소 권한), [shadow_APT](https://github.com/zeldaim/shadow_APT) (모의 통관·물류 플랫폼에서 숨은 경로 찾기).

## 검증

| 방법 | 결과 |
|---|---|
| gitleaks, 이력 전체 | api-security-supply-chain · shadow_APT · shadow-api-lab 0건. ml_detection 공개본은 공개 데이터셋(CSIC) 안의 임의 문자열 22건 외 0건 |
| 실명, `.env`, 공인 IP 검사 | 공개본 0건 |
| 공개 전 원본에서 문제 확인 | 이력에 `.env` 2개와 실명 폴더가 있는 것을 찾아 공개를 보류했다 |

## 전후 비교

| 항목 | 전 | 후 |
|---|---|---|
| ml_detection | 설계와 비밀이 한 레포(이력 포함)에 섞임 | 공개본(이력 새로 시작)과 비공개 원본·보관 레포로 분리 |
| 팀 원본 자료 | ml_detection 이력 안에 | `team-raw-archive`(비공개) |
| 공개 레포 비밀값 | 확인한 적 없음 | 이력 전체 검사 후 공개 |
| 숨은 API | "아무도 모른다"가 방어 | 찾아서 인증·권한으로 막혔는지 확인 |

## 한계와 다음

- 커밋 작성자 이메일은 여러 공개 레포에 이미 남아 있다. 앞으로 GitHub noreply 주소를 쓰는 것을 검토.
- 공개 레포에 비밀값이 다시 들어가지 않도록 CI 에 비밀값 검사를 붙이는 것이 다음 단계다 (OpenSSF Scorecard 와도 연결).
- 한 번 공개한 것은 회수되지 않는다. 공개 전 검사가 사실상 마지막 방어선이다.
