# LFD121 4장 — 공개 설계 (Open Design)

2026-11-17 · 적용한 곳: 내 레포 공개 전환 ([api-security-supply-chain](https://github.com/zeldaim/api-security-supply-chain), [ml_detection](https://github.com/zeldaim/ml_detection) 등)

보안은 설계를 숨기는 데 기대면 안 된다. 설계가 다 알려져도 안전해야 하고, 숨겨야 하는 것은 비밀번호나 키 같은 **작고 바꿀 수 있는 비밀**뿐이다.

## 개념

- Saltzer & Schroeder 의 설계 원칙 중 하나. 암호학의 케르크호프스 원칙과 같은 이야기다 — 알고리즘은 공개돼도 되고, 키만 비밀이면 된다.
- 반대말이 "숨겨서 지키는 보안(security through obscurity)" 이다. 숨긴 것은 언젠가 드러나고(리버싱, 유출, 퇴사자), 드러나는 순간 방어가 통째로 무너진다. 키는 바꾸면 되지만 설계는 바꾸기 어렵다.
- 숨기는 것 자체가 금지는 아니다. **추가 층**으로는 괜찮지만, **유일한 방어**가 되면 안 된다.
- 공개하면 오히려 많은 사람이 검토할 수 있어서 결함을 더 빨리 찾는다. 보안 도구 다수가 오픈소스인 이유이기도 하다.

## 내 프로젝트에서 본 것

### 1) Shadow API 는 "숨겨서 지키는 보안"이 실패한 모양이다

내 API 보안 프로젝트가 찾는 Shadow API(명세에 없는 API)는, 대부분 "아무도 그 주소를 모르니까 괜찮다"는 가정 위에서 살아남는다. 팀 쇼핑몰의 `GET /api/v1/users/{id}` 가 그랬다 — 명세에 없는 옛 경로라 문서에서는 안 보였지만, 인증 없이 남의 정보를 돌려줬다(BOLA). 주소를 숨긴 것은 방어가 아니었다.

→ 내 프로젝트가 하는 일이 곧 이 원칙의 검사다: 숨어 있는 경로를 찾아내고, 숨김이 아니라 **인증·권한**으로 막혀 있는지 확인한다.

### 2) 레포를 공개하면서 "설계"와 "비밀"을 나눴다

| 공개해도 되는 것 (설계) | 숨겨야 하는 것 (비밀) |
|---|---|
| 탐지 룰 생성 방식, 파이프라인 코드, Terraform, 평가 방법 | `.env` 의 JWT 키 · DB 비밀번호, 실명, 원본 운영 로그 |
| → 공개 레포 | → 비공개 보관 레포 `team-raw-archive`, 또는 삭제 |

- 공개 전에 gitleaks 로 이력 전체를 검사했다. `ml_detection` 에서 팀 쇼핑몰 `.env` 2개와 실명 폴더가 이력에 남아 있는 것을 찾았고, 그대로 공개하지 않고 **이력을 새로 시작한 사본**을 공개했다.
- DR 프로젝트의 Terraform 은 공개돼 있지만, DB 비밀번호는 코드에 없고 변수와 SSM 으로 받는다 — 설계가 보여도 비밀은 안 보인다.

### 3) 남은 고민 — 탐지 룰을 공개해도 되나

공격자가 룰을 보고 피해 갈 수 있다는 걱정이 있다. 이 원칙대로 생각하면:

- 룰이 공개돼도 탐지가 유지되도록 만드는 게 맞다 (예: 120초 빈도 룰은 천천히 하면 피해진다 → 실제로 느린 BOLA 를 놓쳤다. 숨겨서 해결할 문제가 아니라 룰을 바꿔야 했다).
- 다만 **운영 중인 실제 임계값**은 키와 비슷하게 바꿀 수 있는 설정값으로 보고 공개본에 넣지 않는다.
